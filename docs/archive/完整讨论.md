# 第一推荐：AI 产品需求洞察 Agent

可以起一个比较像正式产品的名字，比如：

**InsightFlow — AI Product Insight Agent**  
中文：**AI 用户洞察与需求决策 Agent**

它解决一个非常典型的 PM 痛点：

> 产品经理每天面对客服反馈、用户评论、访谈记录、竞品信息、运营数据，信息非常碎片化。Agent 自动完成“反馈 → 洞察 → 优先级 → PRD”的全过程。

这比“AI 聊天机器人”“AI 简历助手”“AI 知识库”强很多，因为它本身就在展示你的**产品经理能力**。

## 整个 Agent 怎么工作

例如你上传：

- 500 条用户反馈
- App Store / 小红书 / Reddit 评论
- 客服聊天记录
- 用户访谈
- 产品需求池
- 竞品信息

Agent 自动完成：

**① 用户反馈理解**

自动判断：

> Bug  
> 功能需求  
> 体验问题  
> 性能问题  
> 价格问题  
> 用户吐槽  
> 潜在需求

并进行去重。

例如：

> “为什么不能批量上传图片？”

> “一次只能传一张太麻烦。”

> “希望增加多图上传。”

Agent 应该识别：

**本质是同一个需求：批量上传。**

---

**② 用户痛点聚类**

Agent 自动形成：

> 支付体验问题：128条  
> 图片上传问题：97条  
> 搜索准确率问题：63条  
> 登录问题：41条

然后可以点击查看：

**每一个结论对应哪些真实用户证据。**

这一点非常重要。

因为普通 LLM 项目只是：

> AI觉得用户需要XXX。

而你的产品是：

> 任何 AI 洞察都必须有 Evidence。

这是非常好的 AI 产品设计点。

# ③ Opportunity Agent

进一步让 Agent 判断：

| 需求 | 用户数量 | 严重程度 | 商业价值 | 开发成本 | 优先级 |
|---|---:|---:|---:|---:|---:|
| 批量上传 | 97 | 高 | 高 | 中 | P0 |
| 夜间模式 | 43 | 低 | 低 | 低 | P2 |
| 搜索优化 | 63 | 高 | 高 | 高 | P1 |

并说明：

**为什么是 P0。**

例如：

> 该需求涉及19.4%的用户反馈，并直接影响核心任务完成率，因此建议进入下一版本。

这就开始体现你的**产品决策能力**。

# 二、最核心的输入是什么？

先让用户上传一个 Excel / CSV。

比如：

| id | 用户反馈 | 用户类型 | 来源 | 时间 |
|---|---|---|---|---|
| 001 | 为什么不能一次上传多张图片 | 普通用户 | 客服 | 10/1 |
| 002 | 图片一张张传太麻烦了 | Pro | App Store | 10/2 |
| 003 | 希望增加批量上传 | Pro | 用户访谈 | 10/3 |
| 004 | 搜索经常搜不到东西 | 普通用户 | App Store | 10/3 |

第一版甚至不用真的爬 App Store、小红书。

**准备 300～1000 条模拟/公开反馈数据就够了。**

因为你先验证的是：

> Agent 有没有能力从大量用户 Voice 中提取 Product Insight。

# 三、第一层：Feedback Classification

每一条反馈先变成结构化数据。

例如原始反馈：

> “每次传照片都只能一个个选，几十张照片我要点半天。”

输出：

```json
{
  "category": "feature_request",
  "module": "image_upload",
  "user_intent": "批量上传图片",
  "pain_point": "单张上传效率低",
  "severity": 4,
  "sentiment": "negative",
  "confidence": 0.93
}
```

你这里要强制用 **Structured Output**。

不要让模型自由发挥。

---

# 四、第二层其实才是项目亮点：需求去重

这是我认为你这个项目最值得做好的地方。

例如：

```text
希望批量上传照片

一次只能上传一张

能不能一次选择多张图片

几十张照片一个个上传太慢

支持多选图片就好了
```

普通程序认为是 5 条需求。

你的 Agent 要识别：

> 都属于同一个需求。

生成：

```text
需求 Cluster #12

批量图片上传

相关反馈：97 条

覆盖用户：71 人

主要痛点：
当前单图片上传导致高频内容创作者操作效率较低。
```

技术实现可以用：

```text
Embedding
      ↓
Vector Similarity
      ↓
初步聚类
      ↓
LLM Cluster Refinement
```

也就是：

**向量相似度负责粗分组**

+

**LLM 负责语义判断**

这个技术路线比完全让 GPT 聚类好很多。

# 五、一定要做 Evidence System

这是我最建议你重点包装的产品设计。

Agent 得出：

> 用户强烈需要批量上传功能。

用户点击：

### 查看证据

弹出：

```text
97 条原始反馈

“为什么不能一次上传多张？”
“每次上传都好麻烦。”
“希望可以批量选择照片。”
“几十张图片一个个传太慢了。”
...
```

也就是说：

```text
Insight
↓
Evidence
↓
Source
```

必须能追溯。

这样你面试的时候就能讲一个非常专业的 AI 产品问题：

> 为避免大模型生成“看似合理但缺少事实依据”的产品洞察，我设计了 Evidence Grounding 机制，要求核心洞察必须引用原始 Voice of Customer 数据。

这句话含金量很高。

# 七、需求优先级不要直接问 GPT

这是另一个非常重要的产品设计。

不要：

> GPT，你觉得这个需求重要吗？

这种项目会很学生。

你可以设计一个：

# Opportunity Score

例如：

```text
Opportunity Score

= 用户覆盖度 × 25%
+ 严重程度 × 25%
+ 反馈增长趋势 × 15%
+ 用户价值 × 20%
+ 商业价值 × 15%
```

然后：

| 需求 | Coverage | Severity | Trend | Value | Score |
|---|---:|---:|---:|---:|---:|
| 批量上传 | 9 | 8 | 8 | 9 | 8.6 |
| Dark Mode | 4 | 3 | 5 | 3 | 3.7 |
| 搜索优化 | 7 | 9 | 7 | 10 | 8.4 |

最终生成：

```text
P0
批量上传

P0
搜索准确率优化

P1
分享功能

P2
Dark Mode
```

而且允许 PM 调整权重。

这样就有产品经理味道了。

# 八、我会加入一个“AI 与 PM 不同意见”的设计

这个功能很适合面试展示。

例如 AI：

> 建议优先开发批量上传。

PM：

> 我认为搜索优化优先级更高。

系统问：

```text
为什么？

○ 商业价值更高
○ 战略方向
○ 开发成本
○ 用户价值
○ 其他
```

PM选择：

> 搜索是核心路径，对留存影响更高。

Agent 更新：

```text
PM Override

AI Priority: #2

PM Priority: #1

Reason:
搜索功能属于核心用户路径，
尽管反馈量低于批量上传，
但其对核心任务完成率影响更大。
```

这一点非常体现：

# Human-in-the-loop

也就是说 Agent **辅助决策，而不是代替产品经理决策**。

当前主流 Agent 框架也专门提供 human review / human-in-the-loop 控制机制；OpenAI Agents SDK 支持审批、guardrails 和 tracing，LangGraph 也把 human-in-the-loop 作为核心工作流能力。:chatgpt-content-reference{index="1"}

# InsightFlow V1 产品需求文档

**产品名称：** InsightFlow  
**产品定位：** AI Product Insight Agent  
**版本：** V1.0 MVP  
**核心目标：** 将大量非结构化用户反馈自动转化为可追溯、可排序、可执行的产品需求洞察。

---

# 1. 产品背景

产品经理在日常工作中会接触大量零散信息：

- 用户反馈
- 客服记录
- App 评论
- 用户访谈
- 社群反馈
- 问卷开放题
- 销售反馈

传统处理方式通常依赖人工阅读、Excel 分类和主观判断，存在几个明显问题：

1. 信息量过大，人工分析效率低。
2. 相同需求表达方式不同，容易重复统计。
3. 产品洞察容易依赖个人经验。
4. 很难证明某个产品判断到底来源于哪些用户反馈。
5. 需求优先级缺乏统一的数据依据。
6. 从“发现问题”到“形成 PRD”存在大量重复工作。

InsightFlow 希望通过 AI Agent 将这一过程标准化。

---

# 2. 产品目标

InsightFlow V1 要解决三个核心问题。

## 2.1 帮助 PM 看懂大量用户反馈

系统自动完成：

用户反馈 → 分类 → 意图提取 → 痛点识别 → 情绪判断

---

## 2.2 找到真正值得关注的问题

系统自动完成：

相似反馈 → 聚类 → 去重 → 用户痛点 → Product Insight

---

## 2.3 将洞察转化为产品行动

系统进一步完成：

Insight → Evidence → Priority → Requirement → PRD

最终形成：

**Voice of Customer → Product Decision**

- 企业级权限系统

这样可以把精力放在真正有价值的 Agent Pipeline 上。

# 14. 聚类技术方案

# 6. 为什么一定要有 intent

这是整个聚类算法一个很重要的设计。

下面两句话：

> “上传太麻烦。”

> “为什么只能一张一张上传？”

如果只 Embedding 原文，第一句话语义不完整。

经过 Agent 后：

```text
module:
image_upload

intent:
batch_image_upload

pain_point:
Repeated file selection when uploading multiple images.
```

它的语义就被标准化了。

因此我建议后面生成一个内部字段：

```text
semantic_text
```

内容是：

```text
Original feedback:
为什么一次只能上传一张？

Module:
image_upload

Intent:
batch_image_upload

Pain Point:
Repeated file selection makes multiple image upload inefficient.
```

然后对这个文本做 Embedding。

这比只 Embed 用户原话更稳定。

# 11. 然后进入最关键的 Clustering

V1 不要搞非常复杂的 Machine Learning。

500 条数据这个规模：

### Step A：Embedding

得到：

```text
F001 → vector
F002 → vector
F003 → vector
...
```

---

### Step B：Cosine Similarity

计算：

```text
similarity(F001,F002)
```

越接近：

```text
1
```

语义越相似。

例如：

```text
“一次只能传一张。”

“希望支持多图选择。”
```

可能非常接近。

---

### Step C：Agglomerative Clustering

我更推荐 Sprint 1 先用：

**Hierarchical / Agglomerative Clustering**

而不是直接 K-Means。

原因很简单：

K-Means 要提前告诉算法：

```text
K = ?
```

真实产品里我们本来就不知道用户到底有多少类问题。

Agglomerative 可以通过：

```text
distance_threshold
```

自动决定形成多少 Cluster。

# 12. Threshold 不要拍脑袋定死

例如初始：

```text
Cosine Similarity ≈ 0.82
```

可以先尝试。

但不要在项目里说：

> “相似度超过0.82就一定是同一需求。”

正确说法应该是：

> 0.82 是 Initial Threshold，通过 Golden Dataset 对 Cluster Purity 与 Coverage 进行评估后调优。

比如：

```text
0.75

Cluster数量：12
Purity：71%
```

```text
0.82

Cluster数量：21
Purity：88%
```

```text
0.90

Cluster数量：47
Purity：95%
但过度拆分
```

最后发现：

```text
0.83
```

效果最好。

这就是一个非常好的面试故事。

```text

↓
```


判断。

例如给 LLM：

```text

3. 为什么文件上传这么慢？

```

Agent 应该判断：

```text
SPLIT
```

```text

```

```text

```

> **LLM semantic refinement**

# 15. Cluster → Insight 不要直接等号

例如 Cluster：

```text
Topic:
Batch Image Upload

28 Feedback
```

这只是“发生了什么”。

我们需要 Agent 再生成：

### Pain Point

```text
Users uploading multiple images must repeatedly
perform the same file-selection operation.
```

### Insight

```text
High-frequency image users experience unnecessary
interaction cost when handling multi-image tasks.
```

### Product Opportunity

```text
Supporting multi-image selection could reduce
repetitive operations in the image upload workflow.
```

注意这里的措辞：

是：

> **could**

而不是：

> 一定能够提高留存率 30%。

因为数据没有告诉我们留存率。

# 16. Evidence 不能让 LLM 自己编

这是我们的铁律：

> **No Evidence, No Insight.**

Evidence ID 必须来自实际数据库：

```text

F102
F183
```

系统后端检查：

```python
evidence_id in cluster_feedback_ids
```

如果：

```text
false
```

直接拒绝 Agent 输出。

这就是一个简单的 **Guardrail**。

# 24. 到这里，InsightFlow 的第一个技术闭环已经确定

最终就是：

```text
Raw Feedback
      ↓
Structured Classification
      ↓
Semantic Representation
      ↓
Embedding
      ↓
Algorithmic Clustering
      ↓
LLM Semantic Refinement
      ↓
Product Insight
      ↓
Evidence Grounding
```

这里实际上已经包含了你以后面试时很好讲的四个 AI 产品设计思想：

**① Structured Output**  
避免不可控的自由文本输出。

**② Hybrid AI Pipeline**  
不是任何问题都交给 LLM，而是 Algorithm + LLM 协作。

**③ Evidence Grounding**  
AI 洞察必须能回溯真实用户反馈。

**④ Evaluation-driven Development**  
通过 Golden Dataset 判断 AI 是否真的改善，而不是凭感觉调 Prompt。
